# FFI: DLL / 共有ライブラリを読み、その関数を呼ぶ。
#
# **POSIX でも呼べるようになった (#133 の段階 2〜3)。** 前はここに
# 「dlopen へ載せ替えれば大半は動くはずだが、stdcall と可変長引数の扱いは
# 別に考える必要がある」と書いてあり、**libffi を入れるかどうかの判断待ちに
# していたが、その判断は要らなかった。**
#
# `src/frontend/win32/dll.cc` の x86_64 の枝は、アセンブリでも libffi でも
# なく**関数ポインタのキャスト**で呼んでいる (`int64_t (*)(int64_t, ...)` へ
# キャストして呼ぶと、**呼び出し規約はコンパイラが出す**)。同じ形を
# src/core/dll-posix.cc に置いた。POSIX x86_64 / aarch64 には規約が 1 つしか
# 無いので、stdcall の区別も要らない。
#
# 実測 (glibc): `abs(-5)` = 5、`getpid()` が `si:getpid` と一致、
# `atoi("42")` = 42、`llabs(-8589934592)` = 8589934592、`strchr` がポインタを
# 返す。`unittest/ffi-portable-tests.l` に 9 件 (**両方のプラットフォームで
# 同じテストになる**)。
#
# **ここに残っているのは 2 種類だけ:**
#
#   * `c-callable-*` 2 件 — **Lisp の関数を C から呼べるアドレスにする**もの。
#     実行時に機械語を作る必要がある (`lc_callable::insn`)。ABI ごとに書くか
#     libffi の closure を使うかの判断が残っている (#133 の段階 4)。
#   * それ以外 — **テストが MSVC のランタイム固有の関数を呼んでいる。**
#     `_itoa` / `_atoi64` / `_i64toa` / `_ui64toa` は msvcrt にしかない。
#     **実装の不足ではない** (同じことを標準 C の関数でやる
#     ffi-portable-tests.l は POSIX でも通る)。
#
# `fix-for-ffi-c-function-return-doubl/float-00` は返り値が double のもので、
# 返り値だけなら POSIX でも通る形に書いてある。**手元の run では
# `.lc` が無いと落ちるが CI では通る**ので、ここに載っているのは別の理由。
#
# **`pack-unpack-*` 4 件はここから外れた。FFI とは関係が無かった。**
# `si:pack-*` / `si:unpack-*` はチャンク (バイト列) を読み書きするだけで DLL を
# 触らない。落ちていたのは core のバグ 2 つで、どちらも `long` の幅:
#
#   * `unpack-int32` が `long` で読んでいた。LP64 では 64bit なので**4 バイトの
#     欄から 8 バイト読み**、32bit からの符号拡張も起きない
#     (0xFFFFFFFF を pack して読むと -1 でなく 4294967295)。固定幅の
#     `int32_t` などに直した。`char` も符号の有無が処理系任せで、**Linux の
#     ARM では符号無し**なので `unpack-int8` が負を返せない。
#   * `make_integer (u_long)` が `int64_t` へ落としていた。LP64 では
#     `make_integer (uint64_t)` が `#if ULONG_MAX != UINT64_MAX` の中にあって
#     **そもそもコンパイルされない**ので、**LONG_MAX を超える符号無し 64bit を
#     一切作れなかった** (全ビット 1 が -1 になる)。
#
# **群の名前を信じて中を見ないと、こういうものが混ざったまま残る。**
# ここに残っているのは本当に LoadLibrary / GetProcAddress / stdcall が要るもの
# だけか、足すときに確かめること。

# ファイル名とパス。
#
# **`chdir-*` 7 件と `fix-truename-*` 4 件はここから外れた。**
#
# 理由は 2 度書き直している。最初は「`chdir` はドライブごとのカレント
# ディレクトリという Win32 の概念に依っている」で、これは違った (`chdir`
# 自体は POSIX でも正しく動く)。次に「`(get-windows-directory)` と
# `(get-system-directory)` が **POSIX では nil を返す**ので、テストが
# Windows のディレクトリを前提にしているだけ」と書いた。**前半は違った:
# nil ではなく未束縛だった。**
#
#     (get-windows-directory)                 => #:unbound
#     (ignore-errors (get-windows-directory)) => #:unbound   (捕まらない)
#
# 値を入れているのは src/frontend/win32/init.cc の `init_windows_dir' だけで、
# POSIX にはそれに当たるものが無い。**未束縛の変数を読むと `#:unbound' という
# 内部の印がそのまま Lisp へ出てくる**: `unbound-variable` にならないので
# `ignore-errors` でも止まらず、**どこにも無い値が `merge-pathnames` や
# リストへ静かに流れていく。** POSIX に Windows ディレクトリは無いので nil を
# 入れた (src/core/environ.cc)。`unittest/environ-tests.l` に 1 件。
#
# **テストの方は「実在する入れ子のディレクトリ」が要るだけだった。**
# `chdir-*` は `(get-windows-directory)` / `(get-system-directory)` を
# `C:\Windows` と `C:\Windows\system32` = 「2 段の入れ子」として使い、
# `fix-truename-*` は `system32\drivers\etc\hosts` を「何段か下にある
# 実在するパス」として使っていただけである。プラットフォームごとに選ぶ形に
# 直した (POSIX は `/usr/` と `/usr/share/`、`/usr/share/zoneinfo/UTC`)。
# **11 件の裏で `chdir` と `truename` が一度も測られていなかった。**
#
# 1 件だけ期待値の意味が違ったので書き換えた。`chdir-6` は 4 つ目の `..` が
# nil を返すことを見ていて、それは「Windows のドライブの根には親が無い」と
# いう形の言い方である。POSIX の `/` の親は `/` 自身なので同じ理屈にならない。
# 測りたいのは**「これ以上は上がれない」**なので、居場所が動かないことで
# 書いた (実装は同じ判定をしていて、POSIX でも根では nil が返る)。
#
# `chdir-3` の `get-disk-usage` は POSIX では nil を返すが、このテストが見て
# いるのは戻り値ではなく**呼んだあとに居場所が戻っているか**なので通る。
# `chdir-4` の `cmd /c dir` は `ls` にした。
#
# **`chdir-path-not-found` はここから外れた。** 前はこのコメントに
# 「POSIX の chdir は ENOENT しか返さないので、区別するには自分で親を辿って
# 確かめるしかない」と書いてあり、**そのとおりだったので、そうした。**
# `file_error (int, lisp)` は**番号とパスの両方を持つ唯一の場所**なので、
# そこで ENOENT のときだけ親を stat して分けている
# (`refine_not_found`、src/core/pathname.cc)。「しかない」で止めずに、
# その手が本当に取れないのかを見ること。
#
#     /no/such/dir/zzz  -> path-not-found  (途中が無い)
#     /tmp/zzz-nope     -> file-not-found  (最後だけ無い)
#
# 1 か所で分けたので chdir だけでなく open や delete-file でも Win32 と
# 同じ条件が付く。
#
# `image-startup-option` と `fix-*load-pathname*-from-dump-image` は
# ダンプイメージに依っている。
#
# **`user-config-path` / `xyzzy-ini-path` は 7 件のうち 5 件が外れた。** 前は
# 「レジストリと ini ファイルに依っている」と 1 行で片付けてあったが、
# **レジストリが要るのは別の話で、ini ファイルの方は移植できた**
# (issue #143)。848 行あった win32/conf.cc のうち Win32 に触っていたのは
# `Get/WritePrivateProfileStringW` の 2 つだけで、残りは書式の処理だった。
# その 2 つを書き (src/core/ini-posix.cc)、残りを core へ移した
# (src/core/conf-io.cc)。**Linux ビルドはそれまで設定を一切読み書きして
# いなかった。**
#
# **残る 2 件も外れた。** `xyzzy-ini-path-XYZZYINIFILE` と
# `user-config-path-XYZZYCONFIGPATH` は ini とは関係が無く、**環境変数を
# 子プロセスへ渡す方の問題**だった: 非 Win32 の `call-process` /
# `make-process` が `:environ` を丸ごと無視していた (`Kenviron` が
# ncurses-process.cc に出てこなかった)。実装した (`build_environ`)。
# **この 7 件の群は空になった。**
#
# **`directory--*` 5 件はここから外れた。** 前はこのコメントに
# 「WIN32_FIND_DATA の属性 (FILE_ATTRIBUTE_*) をそのまま見ている」と
# 書いてあったが、**5 件のどれも属性を見ていなかった。** 測り直したら
# 別々の 3 つの理由で、全部直せた:
#
#   * `get-file-info` が **ncurses-stubs.cc で nil を返すスタブ**だった。
#     中身は `strict_get_file_data` を呼んで `make_file_info` に渡すだけで、
#     その `WINFS::get_file_data` は非 Win32 でも stat で実装済み。
#     `#ifdef _WIN32` の中にあっただけで、**`directory` の `:file-info t` は
#     同じ `make_file_info` を通って動いていた** (片方だけ空だった)。
#   * `:show-dots t` が `./` と `../` を返さなかった。Win32 の
#     FindFirstFile はこの 2 つを返し、**弾くのは呼び出し側の仕事**
#     (glob.cc の DF_SHOW_DOTS) なのに、vfs-posix.cc が先に落としていた。
#   * `(merge-pathnames "/work/etc" "c:/hoge")` が **"c:/work/etc"** を
#     返していた。ドライブの無い rooted パスに defaults のドライブを被せる
#     のは Win32 では正しいが、POSIX には被せるドライブが無いので嘘になる。
#
# **属性を見ているという理由は、テストを読めば違うと分かるものだった**
# (`directory--absolute` は `merge-pathnames` に `c:/hoge` を渡している)。
# 分類を書くときは、テストが実際に何を呼んでいるかを見ること。
#
# **エラーの番号と文言はここから外した。** POSIX では `GetLastError ()` が
# errno を返すのに `ERROR_*` は Win32 の番号のままで、両者が同じ整数の欄に
# 混ざっている。文言 (src/core/lprint.cc) と `create-directory` の既存判定は

# コマンドライン引数の処理 — **この群も空になった。**
#
# ここには 26 件 (`process-command-line--*` 25 件と
# `fix (cdr '#1='#1#) printing`) が並んでいて、「POSIX では子プロセスが同じ
# tty を取り合うので測れない」と書いてあった。**原因の見立ては当たっていて、
# 直せば通った。**
#
# どれも自分自身をもう 1 つ起動して引数の効きを見る。子に `--batch` を
# 付けないと、子が親と同じ tty で curses を初期化しようとして、どちらも
# 進まない (結果ファイルが書かれず "result not sent."、`call-process` は 1)。
# コマンド行を組む所を `unittest/simple-test.l` の `test-self-command` に
# まとめ、端末ビルドでは `--batch` を足すようにした。
#
# 2 件だけ別の理由だった: `-e(view-mode)` と `-eval (view-mode)` は
# **括弧がシェルに食われていた。** POSIX では子プロセスを `/bin/sh -c` で
# 起動するので `(` が構文エラーになる (cmd.exe はここでは括弧を特別扱い
# しないので Windows では通っていた)。このファイルの他の指定は最初から
# `-e \"~S\"` の形で引用符に囲まれていて、この 2 つだけが漏れていた。

# ウィンドウの分割と構成、エコー領域 — **この群は空になった。**
#
# ここには 27 件が並んでいて、「`--batch` には画面が無いから仕方ない」と
# 書いてあった。**それが間違いだった。** 原因は画面の有無ではなく、
# `compute_geometry` が `getmaxyx (stdscr, ...)` を直に呼んでいたことである。
# `--batch` では curses を上げないので `stdscr` が 0 で、`getmaxyx` は
# rows も cols も -1 にする。それで `app.active_frame.size` が毎回 -1 に
# 上書きされ、`create_batch_windows` が置いていた 80x24 が消えていた。
# その結果すべてのウィンドウの矩形が潰れ、`split-window` は「分割できません」、

# mingw でも落ちるもの。**POSIX 固有ではない。**
#
# **理由を測り直した。以前ここには「端末ビルドと mingw ビルドが同じ結果を返し、
# MSVC だけが違う。理由が分かっていない」と書いてあった。** 結果が同じだったのは
# 端末側が**引数をそのまま返すスタブだった**からで、理由は分かった。
#
# `abbreviate-display-string` は**幅を測る単位がプラットフォームで違う。**
# Win32 は GDI で可変幅フォントのピクセルを測り、上限は「平均文字幅 x 引数」
# である。端末は文字セルの格子なので桁で測る (src/core/abbrev-columns.cc)。
#
#     (abbreviate-display-string "D:/src/cmigemo-1.3c-MIT/src/wordlist.h" 40 t)
#
# この入力は 38 文字で、**桁で数えれば 40 に収まるので縮めないのが正しい。**
# MSVC では 40 文字ぶんの平均幅に収まらないので縮む。**どちらも正しく、
# 期待値が片方の環境のフォントの寸法を焼き付けている。**
#
# mingw (Wine) でも落ちるが、**そちらは理由が違う**: 実装は同じ GDI の経路で、
# Wine のフォントの寸法が本物の Windows と違う。
#
# 端末側の実装は入れた。`unittest/abbrev-tests.l` に 7 件あり、**どちらの
# 数え方でも成り立つ性質**で書いてある (十分長いものは縮む、`...` が入る、
# 末尾のファイル名は残る)。桁数そのものを見る 2 件だけ POSIX 限定。

fix-abbreviate-display-string
