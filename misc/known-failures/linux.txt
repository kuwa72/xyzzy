# FFI: DLL / 共有ライブラリを読み、その関数を呼ぶ。
#
# **POSIX でも呼べるようになった (#133 の段階 2〜3)。** 前はここに
# 「dlopen へ載せ替えれば大半は動くはずだが、stdcall と可変長引数の扱いは
# 別に考える必要がある」と書いてあった。
#
# 最初は libffi 無しで通した。`src/frontend/win32/dll.cc` の x86_64 の枝は、
# アセンブリでも libffi でもなく**関数ポインタのキャスト**で呼んでいる
# (`int64_t (*)(int64_t, ...)` へキャストして呼ぶと、**呼び出し規約は
# コンパイラが出す**)。同じ形を src/core/dll-posix.cc に置いた。POSIX x86_64 /
# aarch64 には規約が 1 つしか無いので、stdcall の区別も要らない。
# **そのあと libffi に置き換えた** — 理由は下の可変長引数の節。
#
# 実測 (glibc): `abs(-5)` = 5、`getpid()` が `si:getpid` と一致、
# `atoi("42")` = 42、`llabs(-8589934592)` = 8589934592、`strchr` がポインタを
# 返す。`unittest/ffi-portable-tests.l` に 9 件 (**両方のプラットフォームで
# 同じテストになる**)。
#
# **20 件がここから外れた。「テストが msvcrt 固有の関数を呼んでいる」という
# 分類は、半分しか当たっていなかった。**
#
# 前はここに「残っているのは c-callable の 2 件と、テストが `_itoa` /
# `_atoi64` / `_i64toa` / `_ui64toa` を呼んでいるもの」と書いてあった。
# **実際には、落ちていた大半が `"msvcrt"` を `dlopen` できないだけだった。**
# `unittest/foreign-test.l` はライブラリ名を決め打ちしていたので、
#
#     (sprintf 0 0 123)
#     期待: 「不正な可変長引数です: 123」
#     実際: 「共有ライブラリを読み込めません: msvcrt: cannot open ...」
#
# となる。**`funcall-invalid-vaargs-*` 7 件は型を検査するだけで関数を呼ぶ所まで
# 行かない**ので、プラットフォームとは何の関係も無かった。ライブラリ名を
# `foreign-test-libc` で選ぶようにしたら 19 件通った。
#
# msvcrt にしか無いのは `_itoa` / `_ultoa` / `_i64toa` / `_ui64toa` の 4 つだけ
# で、POSIX では `sprintf` に書式を渡して同じことをする (経路は固定引数から
# 可変長引数に変わるが、測っているのは「その幅の整数が C 側に正しく届くか」で
# 同じ。**符号無し 64 ビットで最上位ビットが立っている場合**が本番)。
#
# **副作用で 2 つ見つかった。どちらも「落ちないようにする」方の直しである。**
#
#   * 可変長引数に `c:double` を渡すと **SIGSEGV でエディタが死んだ。**
#     src/core/dll-posix.cc には「ビット列を整数の枠で渡す。受け側が整数として
#     読むなら通る」と書いて通していたが、**SysV x86_64 では `al` に
#     「ベクタレジスタを何本使ったか」を入れる約束**があり、整数の関数型へ
#     キャストして呼ぶと `al` が 0 になる。呼ばれた側はレジスタ保存領域の
#     浮動小数の欄を埋めないまま読む。1 個だけなら直前の xmm に残った値で
#     偶然合うことがあり、それが「通ることもある」の正体だった。**断るように
#     した** (固定引数の float / double と同じ扱い)。
#   * SEH のテスト 3 件が **SIGFPE / SIGSEGV でスイートごと落ちるようになった。**
#     以前は `div` / `strcat` を "msvcrt" から引いていて `dlopen` に失敗して
#     いたので、**無害に落ちていただけ**である。ライブラリ名を直したら本当に
#     0 除算が起きた。**既知失敗に載せる話ではない** (走った時点で終わり) ので、
#     `#-unix` で走らせないようにした。
#
# **可変長引数の 4 件はここから外れた。libffi を入れたので。**
#
# 上の「libffi を入れるかどうかの判断は要らなかった」は**半分だけ当たって
# いた**: 整数とポインタはキャストで足りたが、**float / double には届かない。**
# 固定引数はレジスタ列が別なので渡る場所が違い、可変長引数は `al`
# (使ったベクタレジスタの本数) が 0 になって呼ばれた側が浮動小数の欄を
# 埋めないまま読む。**2 個目で SIGSEGV。**
#
# **Win64 に同じ問題が無いので Wine のジョブではこの 4 件が通っていた。**
# 「Windows で通るなら実装が正しい」が成り立たない例である。
#
# libffi は `ffi_prep_cif_var` で可変長引数を扱える。格上げ (char/short -> int、
# float -> double) は呼ぶ側の仕事だが、`check_vaarg_type`
# (src/core/dll-call.cc) が既にやっていた — Win32 側も同じ関数を通るので、
# 書き足すものは無かった。`libffi-dev` が Linux ビルドの必須の依存に増えた
# (tools/devenv/Dockerfile と .github/workflows/linux.yml)。
#
# **`c-callable` の 3 件もここから外れた (#133 の段階 4)。** Lisp の関数を
# C から呼べるアドレスにするもので、libffi の `ffi_closure` で書けた。
#
# **置き場所だけが Win32 と違った。** Win32 は `lc_callable::insn[64]` に機械語
# を書き、**その配列そのもの**のアドレスを C へ渡す (ABI ごとに 3 通りの機械語が
# src/frontend/win32/dll.cc にある)。libffi の closure は**自分で実行可能な
# メモリを確保して別のアドレスを返す**ので配列に入らず、**POSIX の Lisp ヒープは
# 実行可能でない**のでそこへ機械語を書く手も取れない。非 Win32 では `insn[]` の
# 代わりにポインタ 2 本を持ち、C へ渡すアドレスを `xc_callable_address`
# (src/core/dll.h) が選ぶ形にした。
#
# `Fsi_make_c_callable` は core (src/core/dll-call.cc) へ移した。型を検査して
# 枠を埋めて `init_c_callable` を呼ぶだけで、**プラットフォームに依るのはその
# `init_c_callable` だけ**だった。
#
# **残る `defun-c-callable-stdcall` は c-callable の話ではない。** これは
# `EnumWindows` に callback を渡すテストで、**user32 が無いので `dlopen` の所で
# 止まる。** 呼び出し規約の `:stdcall` は POSIX では既定の 1 つに落ちるだけで、
# 問題にならない。下の Win32 API の群に移した。
#
# **ここに残っているのは 2 種類:**
#
#   * `last-win32-error` 2 件 — `MultiByteToWideChar` と `GetLastError` を
#     kernel32 から引く。**POSIX に相当するものが無い。**
#   * `wait-object-*` 2 件 — 待機可能オブジェクト。同じく相当物が無い。
#
# **`pack-unpack-*` 4 件はここから外れた。FFI とは関係が無かった。**
# `si:pack-*` / `si:unpack-*` はチャンク (バイト列) を読み書きするだけで DLL を
# 触らない。落ちていたのは core のバグ 2 つで、どちらも `long` の幅:
#
#   * `unpack-int32` が `long` で読んでいた。LP64 では 64bit なので**4 バイトの
#     欄から 8 バイト読み**、32bit からの符号拡張も起きない
#     (0xFFFFFFFF を pack して読むと -1 でなく 4294967295)。固定幅の
#     `int32_t` などに直した。`char` も符号の有無が処理系任せで、**Linux の
#     ARM では符号無し**なので `unpack-int8` が負を返せない。
#   * `make_integer (u_long)` が `int64_t` へ落としていた。LP64 では
#     `make_integer (uint64_t)` が `#if ULONG_MAX != UINT64_MAX` の中にあって
#     **そもそもコンパイルされない**ので、**LONG_MAX を超える符号無し 64bit を
#     一切作れなかった** (全ビット 1 が -1 になる)。
#
# **群の名前を信じて中を見ないと、こういうものが混ざったまま残る。**
# ここに残っているのは本当に LoadLibrary / GetProcAddress / stdcall が要るもの
# だけか、足すときに確かめること。

# Win32 API を直接呼ぶもの。
# 
# **理由を測り直した。** 前はここに「`last-win32-error` 2 件は GetLastError
# ではなく FFI で止まっている。上の FFI 群と同じ理由なので、そちらが動けば
# 一緒に通るはず」と書いてあった。**FFI は動くようになったが、この 2 件は
# 通らなかった。** 止まっているのは呼ぶ側ではなく**呼ぶ相手**で、
# `MultiByteToWideChar` は kernel32 の中にあり、**kernel32 は POSIX に無い。**
# `wait-object` は WaitForMultipleObjects で、同じく相当物が無い。
#
# **`defun-c-callable-stdcall` は上の FFI 群から移した。** callback を作る所
# (`si:make-c-callable`) は POSIX でも動くようになったが、このテストが渡す
# 相手が `EnumWindows` なので、**user32 を `dlopen` する所で止まる。**
# `:stdcall` の指定は POSIX では既定の規約 1 つに落ちるだけで問題にならない
# ので、**「呼び出し規約が要る」ではなく「その API が無い」側**である。
#
# **`machine-type` はここから外れた。** 「GetSystemInfo」と書いてあったが、
# **POSIX でも `machine-type` は値を返していた** ("amd64")。落ちていたのは
# テストの期待値が `#+x86 "x86" #+x64 "x64" #+ia64 "IA64"` で、**POSIX の
# 名前 (amd64 / aarch64) を書いていなかったため期待値が空になっていた**から。
# 期待値に足した。
#
# **`add-putenv-04` と `test-environ-*` 3 件はここから外れた。** 前は
# 「Win32 の環境変数ブロック」と書いてあったが、**環境変数ブロックは
# 関係が無く、2 つ別の話だった**:
#
#   * `si:putenv` が POSIX で**成功を返して何もしていなかった。**
#     POSIX の `putenv` は渡した文字列を**複写せずポインタを環境に置く**のに、
#     `alloca` で積んだ文字列を渡していた。`setenv` / `unsetenv` に直した
#     (Win32 の `_wputenv` は複写するので、あちらは正しい。**同じ名前で
#     約束が違うものを platform.h で別名にしてはいけなかった。**)
#   * `test-environ-*` の突き合わせ相手が `cmd.exe /c set` だった。
#     POSIX では `env` を使う形にした。**この 2 件が POSIX で測れていれば
#     putenv の壊れ方は捕まっていた** — 「外の目」を Windows 専用にすると、
#     そこで守られるはずの性質が丸ごと測られなくなる。
# `handle-access-violation` / `handle-divide-by-zero` はハードウェア例外を
# win32-exception として受け取るもので、SEH が要る。
#
# **`fix-start-timer` はここから外れた。** 「Win32 の環境変数ブロック」の
# 群に混ざっていたが、`start-timer` は環境変数と関係が無い。`utimer` の
# **OS に触っている部分は `SetTimer` / `KillTimer` の 2 つだけ**で、残りは
# 待ち行列の管理だった。core へ移し (src/core/utimer.cc)、POSIX では端末の
# `select` の待ち時間を次の期限に合わせる形にした。
#
# **1 件の既知失敗の裏に、測られていない機能が 2 つあった。**
# `lisp/ts.l` の tree-sitter ハイライトの遅延更新と `lisp/grepd.l` の
# 非同期 grep が `start-timer` を使っていて、どちらも黙って動かなかった。
#
# 直す途中で platform.h の時刻の 2 つのバグも出た:
# **`GetSystemTime` が `wMilliseconds` を 0 に固定していた** (SYSTEMTIME を
# 通る時刻の分解能が 1 秒で、0.05 秒のタイマが秒が変わるまで来ない) と、
# **`SystemTimeToFileTime` が `mktime` (ローカル時刻) を使っていた**
# (`GetSystemTime` は `gmtime` で作るので round trip がタイムゾーンの分だけ
# ずれる。TZ=UTC のコンテナでは見えなかった)。
# `formatter-*` は外部の整形コマンドを Win32 のプロセス起動で呼ぶ。
#
# **`shell-operation-*` 15 件はここから外れた。** SHFileOperation を呼んで
# いるので「Win32 API を直接呼ぶもの」に分類してあったが、**呼んでいる API が
# Win32 なだけで、やること (複写・移動・削除) は移植できた。** core の
# ファイル操作で組み直した (src/core/pathname.cc の非 Win32 側)。
# 落としたのは進捗ダイアログ・ごみ箱への undo・上書き確認という見た目だけ。
#
# **`uuid-create-*` 8 件もここから外れた。** 前はこのコメントに
# 「CoCreateGuid には uuid_generate があるので移植できる余地がある」と
# 書いてあり、そのとおりだった。**ただし libuuid には依存しなかった** —
# RFC 4122 の中身は「乱数」(version 4) か「時刻 + 機械の識別子」
# (version 1) で、`/dev/urandom` と `clock_gettime` で足りる。Linux ビルドの
# 依存は ncurses と zlib だけに保ちたいので、そちらを選んだ
# (src/core/system.cc の非 Win32 側)。
#
# **この群に残っているものは、名前が Win32 API だからではなく、
# 「その API がやっていること自体が POSIX に無い」から残っている。**
# SEH (ハードウェア例外を Lisp のコンディションとして受け取る) と
# レジストリは無い。分類を書くときはそこを見分けること。
#
# **`formatter-*` 2 件はここから外れた。** テストが偽フォーマッタを
# `cmd /c ...` で書いていただけで、POSIX では 1 つも起動できていなかった。

#
# **落ちて見えていたのは「成功して内容が変わる」経路の 2 件だけだったが、

# ファイル名とパス。
#
# **`chdir-*` 7 件と `fix-truename-*` 4 件はここから外れた。**
#
# 理由は 2 度書き直している。最初は「`chdir` はドライブごとのカレント
# ディレクトリという Win32 の概念に依っている」で、これは違った (`chdir`
# 自体は POSIX でも正しく動く)。次に「`(get-windows-directory)` と
# `(get-system-directory)` が **POSIX では nil を返す**ので、テストが
# Windows のディレクトリを前提にしているだけ」と書いた。**前半は違った:
# nil ではなく未束縛だった。**
#
#     (get-windows-directory)                 => #:unbound
#     (ignore-errors (get-windows-directory)) => #:unbound   (捕まらない)
#
# 値を入れているのは src/frontend/win32/init.cc の `init_windows_dir' だけで、
# POSIX にはそれに当たるものが無い。**未束縛の変数を読むと `#:unbound' という
# 内部の印がそのまま Lisp へ出てくる**: `unbound-variable` にならないので
# `ignore-errors` でも止まらず、**どこにも無い値が `merge-pathnames` や
# リストへ静かに流れていく。** POSIX に Windows ディレクトリは無いので nil を
# 入れた (src/core/environ.cc)。`unittest/environ-tests.l` に 1 件。
#
# **テストの方は「実在する入れ子のディレクトリ」が要るだけだった。**
# `chdir-*` は `(get-windows-directory)` / `(get-system-directory)` を
# `C:\Windows` と `C:\Windows\system32` = 「2 段の入れ子」として使い、
# `fix-truename-*` は `system32\drivers\etc\hosts` を「何段か下にある
# 実在するパス」として使っていただけである。プラットフォームごとに選ぶ形に
# 直した (POSIX は `/usr/` と `/usr/share/`、`/usr/share/zoneinfo/UTC`)。
# **11 件の裏で `chdir` と `truename` が一度も測られていなかった。**
#
# 1 件だけ期待値の意味が違ったので書き換えた。`chdir-6` は 4 つ目の `..` が
# nil を返すことを見ていて、それは「Windows のドライブの根には親が無い」と
# いう形の言い方である。POSIX の `/` の親は `/` 自身なので同じ理屈にならない。
# 測りたいのは**「これ以上は上がれない」**なので、居場所が動かないことで
# 書いた (実装は同じ判定をしていて、POSIX でも根では nil が返る)。
#
# `chdir-3` の `get-disk-usage` は POSIX では nil を返すが、このテストが見て
# いるのは戻り値ではなく**呼んだあとに居場所が戻っているか**なので通る。
# `chdir-4` の `cmd /c dir` は `ls` にした。
#
# **`chdir-path-not-found` はここから外れた。** 前はこのコメントに
# 「POSIX の chdir は ENOENT しか返さないので、区別するには自分で親を辿って
# 確かめるしかない」と書いてあり、**そのとおりだったので、そうした。**
# `file_error (int, lisp)` は**番号とパスの両方を持つ唯一の場所**なので、
# そこで ENOENT のときだけ親を stat して分けている
# (`refine_not_found`、src/core/pathname.cc)。「しかない」で止めずに、
# その手が本当に取れないのかを見ること。
#
#     /no/such/dir/zzz  -> path-not-found  (途中が無い)
#     /tmp/zzz-nope     -> file-not-found  (最後だけ無い)
#
# 1 か所で分けたので chdir だけでなく open や delete-file でも Win32 と
# 同じ条件が付く。
#
# **ダンプイメージの 2 件は両方とも外れた。** 理由は「ダンプイメージに
# 依っている」と 1 行で書いてあったが、測ったら**そもそも POSIX でダンプが
# 動くかを誰も測っていなかった** (issue #217 -> #219)。書く側は前から動いて
# いて、読む側が繋がっていなかっただけだった (762ms -> 206ms)。
#
#   * `image-startup-option` -- ダンプを一切していないテストで、
#     `-image <path>` が `(si:dump-image-path)` に入るかしか見ていない。
#     落ちていたのは「オプションが読まれていない」から。
