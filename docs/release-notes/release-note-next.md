変更
----

  * Win32 のターミナルバッファで、日本語入力の変換ウィンドウが入力欄では
    なく「最後に文字が描かれた場所」に出ていたのを直した。Claude Code の
    ような、入力欄がありつつ画面がリアルタイムに更新される TUI で顕著
    だった。原因は 2 つ重なっていた。

    1 つめ: **ターミナルのカーソルが Windows キャレットではなかった。**
    ターミナルは自前のブロックカーソルを `InvertRect` で描き、Windows
    キャレットは「位置だけ合わせて隠す」扱いだった。IME (特に近年の TSF
    ベースの MS-IME) は `ImmSetCompositionWindow` で教えた位置より可視
    キャレットを優先することがあり、キャレットが隠れたままだと位置を
    いくら教えても変換ウィンドウが古い場所に居座った。エディタ側
    (キャレット可視) では IME の位置が正しく出る実績があるので、同じ形に
    する: `InvertRect` をやめ、**Windows キャレットそのもの** (セル幅の
    ブロック、XOR なので見た目は反転で同じ) をターミナルのカーソルとして
    出す。点滅するようになるのは実際の端末と同じ挙動である。

    DECTCEM (CSI ?25l) でカーソルが消されている間は普段はキャレットも
    見せないが、**位置は常に追従**させる (Ink 系 TUI はカーソルを隠した
    まま毎フレーム末に論理的な入力位置へ CUP する。放置すると変換開始
    時に「最後にキャレットが見えていた頃」の無関係な位置に変換ウィンドウ
    が出る)。さらに **IME の変換中だけは DECTCEM 中でもキャレットを
    見せる**。可視キャレットが無いと上記の IME が位置を見失うためで、
    変換 UI がすぐ上に被さるので二重表示の実害はほぼ無い。

    なお Claude Code が実カーソルをどう扱うかは pty 越しに生のエスケープ
    列を取って確認した。frame 毎に `?2026h ?25l … CUP(入力欄) ?25h ?2026l`
    で、**実カーソルは毎フレーム末に入力欄へ置かれ可視**である。つまり
    位置情報は端末側に正しく届いていて、それをキャレットに反映する側の
    問題だった。

    2 つめ: **reader thread と描画の間にロックが無かった。** `Terminal`
    (格子・カーソル・dirty) は pty の reader thread が `feed ()` で書き、
    GUI thread が描く。排他が無いので GUI が feed の途中の状態 (カーソルは
    文字を書いた直後) を描くことがあり、そこで `clear_dirty` すると、
    その chunk に 1 frame 丸ごと入っていた場合は feed 完了時に dirty が
    立たず (カーソルは動いて戻ったので前後比較は「変化なし」、セル書き
    換えの分は途中で消された)、誰も描き直さないままカーソルが取り残されて
    止まる。出力が続く限り次の描画で直るので、リアルタイム更新の多い TUI
    で「出力が止まった瞬間」に固まって見える。feed 一回と「描画 +
    clear_dirty」をそれぞれ排他して、描く側が見るのは必ずどこかの feed
    完了時点の状態、と保証した。リサイズによる格子の realloc が feed の
    書き込みと衝突し得た穴も同じロックで塞がる。

    ついでに周辺で見つかったものを直した。

      * dirty を落とすのを描画の後から前に変えた。描いた直後に reader が
        食わせた分は今描いた絵に入っていないので、後で落とすとその分の
        通知が消え、次の出力まで画面に出ない。synchronized update
        (CSI ?2026h) で隠されている間は落とさない (`t_dirty` は 2026l の
        あとで溜めた分を見せるための印なので、出力と無関係に走る refresh
        が消してはいけない)。
      * reader 側は `dirty ()` を見てから GUI に通知していたが、GUI が
        dirty を落とす瞬間と重なると通知が飛ばなかった。食わせたら必ず
        一度起こす (通知は `p_pending` でまとめられるので負荷は同じ)。
      * WM_PAINT からターミナルを描く経路 (リサイズ直後など `refresh ()`
        を通らない) でもキャレットを出し直すようにした。
      * カーソル行の強制再描画 (反転セルの消し残し対策) は、カーソルを
        セルに描き込まなくなったので不要になり、削除した。

    **これでも直らない残りの症状について。** Claude Code で、直前の入力
    から少し間を置いてから日本語入力を始めると、変換ウィンドウが画面の
    右端 (アイドル時に再描画される状態表示らしき位置) に出ることがある。
    調査用ログを一時的に仕込んで実機で追ったところ、その瞬間の
    `Terminal` の内部状態 (パース結果そのもの) が既にその位置を指して
    いた — つまり xyzzy 側の取りこぼしではなく、**アプリ自身が実カーソル
    をその位置に置いたまま、次の実入力が来るまで入力欄へ戻していない**。
    xyzzy はターミナルの実カーソル位置をそのまま信じる以外に IME の置き
    場所を決める手段が無いので、ここは直しようがない。アプリ側 (Ink 系
    レンダラ) がアイドル時の再描画で実カーソルを入力位置に戻し忘れている
    ことが原因と見ている。
